# 現状とロードマップ

## v0.9.0の運用基準

通常の起動・一覧表示・静止中は必要な読み込みと描画だけを行う。明示された3Dプレビュー、詳細表示、サムネイル生成、印刷準備に処理を割り当て、中止後はリソースを解放する。

| 操作 | 現在の動作 |
| --- | --- | --- |
| 起動と監視 | 保存済みSQLiteカタログから一覧を開く。初回の監視通知を登録に再利用し、監視で確認できなかった登録パスだけを個別照合する。 |
| 3Dプレビュー | 3MFと大きいSTLの解析を中止可能なワーカーで実行する。WebGLは形状確定後に初期化し、静止時は描画を停止する。 |
| 大きい3MF | 3D読み込みに失敗したときは、ZIPから範囲読み込みした対応画像を表示する。明示した詳細読み込みに保存済みの予算を適用する。 |
| サムネイル | 画像をSQLiteのBLOBに保存し、画面には必要な画像だけをバイナリ配信する。一括生成は1つの作業用レンダラーで1件ずつ処理する。 |
| 配布 | ビルド済み画面と重複していた依存ライブラリを除き、実行時に必要な依存ファイルとライセンスを同梱する。 |

### v0.9.0の測定記録

| 測定条件 | 結果 |
| --- | --- |
| Windows配布版をv0.8.0と比較 | `app.asar` は76.72 MBから23.48 MB、配布フォルダ全体は423.10 MBから369.92 MB。 |
| 合成モデル1,000件の監視開始 | Chokidarの初回走査に加えて行っていたディレクトリ走査11件とモデルのファイル情報取得1,000件を省いた。 |
| 合成3MF・25万三角形を同じ環境でプレビュー | レンダラーのピーク実メモリは約313 MiBから235 MiB。単発測定で、モデル構成や環境によって変動する。 |

## 次に改善する項目

| 優先 | 残る制約 | 次の完了条件 |
| --- | --- | --- |
| P1 | 一覧は48件ずつ描画する。検索・並べ替えと状態通知は全件のメタデータを扱い、旧JSONの初回移行もファイル全体を読む。 | 大規模カタログで、SQLでの絞り込み・ページ取得、差分通知、旧形式の分割移行を比較する。件数別に応答時間とピークRAMを記録する。 |
| P1 | 大きなモデルは、解析のあとも初回のGPU転送と描画に時間がかかる。 | STL・STEP・3MFでピークRAM、初回表示時間、キャンセルから復帰までの時間を測る。段階表示を入れる場合は寸法と配置の検証も行う。 |
| P1 | Studioに渡した後のスライス時間やメモリ、送信結果はStudioとプリンタ側で決まる。 | 実機でSTL・既存3MF・SCAD由来STLの代表ケースを確認し、スライス結果と送信結果を再現可能な手順にまとめる。 |
| P2 | IPCの引数や応答を各実装点で定義しており、mainやlibraryの変更が広がりやすい。 | 機能単位でハンドラーの責務を小さくし、IPCの契約を型付きで共有する。 |
| P2 | 配布と印刷準備の検証対象はWindows・Bambu Studio。 | 対応を増やす際には、スライサー別アダプタと配布物の検証手順を先に用意する。 |
