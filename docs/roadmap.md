# v0.5.0の評価とロードマップ

v0.5.0は少数のモデルを開くデモとしては成立していた。実用ライブラリとしては、1件の変更がライブラリの全件処理につながり、3D表示を必要としない利用にも形状解析のコストを払わせる設計だった。

| 重大度 | 旧版の欠陥 | v0.6.0での対応 |
| --- | --- | --- |
| P0 | メモ1件やサムネイル1枚の変更で、画像を含むライブラリ全体をJSONへ再書き込み。保存失敗時にメモリの変更だけが残る経路もあった。 | SQLiteの対象行だけをトランザクションで更新。コミット後にメモリへ反映。旧JSONを保持し、破損時はエラーを出す。 |
| P0 | サムネイル付き全件の状態を画面へ送り直し、全カードと画像を並べていた。登録数に応じてアプリを開くだけで消費が増えた。 | 画像をBLOBに分離し、表示付近の画像だけを取得。カードは48件ずつ。起動時は保存済み一覧を表示してからフォルダを照合。 |
| P1 | モデルを選ぶだけで解析を開始。高解像度のWebGLと影を有効にし、静止中も描画コールバックを回していた。大きい予算を設定して使う前提だった。 | 標準を軽量モードに変更。明示操作で3Dを読み込み、読込予算0.5 GiBと画像サイズを制限。静止中の描画を止め、古いファイル読込を中止。 |
| P1 | 公開パラメータの変更が画面にしか残らず、モデルの再選択や再起動で再現できなかった。 | モデル別の名前付きプリセットをSQLiteへ保存。OpenSCAD CustomizerのJSONを出し入れし、ソース変更後は現在の定義で再検証。 |
| P1 | Bambu連携はファイルを開くだけで、SCADは手動STL出力が必要。引き渡しと印刷完了の区別も画面に出なかった。 | 詳細から印刷準備を開始。STL・STEP・3MFは元ファイルを渡し、SCADは編集中の値で一時STLを作る。スライスとプリンタ送信はStudioで確定する。 |

## 実装順と完了条件

1. **永続化と移行。** 旧データの件数・画像・ユーザー設定を保持し、失敗時のロールバック、再起動、並行監視をテストする。
2. **軽い一覧と3Dの分離。** 一覧を開くだけでWebGLを動かさず、重い3MFを軽量上限で断れることを確認する。上限に達しても、登録とStudioへの引き渡しを使えるようにする。
3. **再利用できるOpenSCAD設定。** SQLiteを再度開いて適用でき、書き出したJSONを実際のOpenSCADで読めることを確認する。
4. **印刷ワークフロー。** 元のプロジェクト設定を保持した受け渡し、SCADのディスクだけを使う準備、中止、エラー表示を検証する。実機送信の検証では、印刷先と設定の確定をStudioの画面で行う。

合成データ1,000件と各16 KiBのサムネイルで、Nodeのヒープ上限を128 MiBにして移行を検証した。旧JSONは約22.3 MB、画像を含まない新しい一覧状態は約461 KB。全画像を保持し、メモを1件変更したときに更新したSQLiteの行は1行だった。この測定には3D解析、V8以外のメモリ使用量、ハードウェアの速度差を含まない。

## 次に改善する項目

| 優先 | 残る制約 | 次の完了条件 |
| --- | --- | --- |
| P1 | 初回だけは旧JSON全体をメモリへ読む。表示カードを制限しても検索・並べ替えと状態通知のメタデータは全件分。 | 大きな旧ライブラリを分割移行し、SQLによる絞り込み・ページ取得と差分通知で応答時間を測る。 |
| P1 | STL・3MFの解析には同期処理があり、制限内でも複雑な形状では待つ。予算はOSによるRAM上限ではない。 | 解析を中止可能なワーカーで実行。大きい3MFはZIPの範囲読込で内蔵画像を先に出し、選択切替とキャンセルの応答を測る。 |
| P1 | Studioに渡した後のスライス時間やメモリ、送信結果はStudioとプリンタ側で決まる。 | 実機でSTL・既存3MF・SCAD由来STLの代表ケースを確認し、スライス結果と送信結果を再現可能な手順にまとめる。 |
